# QU-AI-GUARD

**AI-Guarded Quantum Key Distribution for Secure Satellite-to-Ground Communication**

A fully local, pure-software capstone that combines **real quantum BB84 key
exchange** (running on the Qiskit-Aer circuit simulator) with a **machine-learning
guard** that auto-tunes the link and detects eavesdroppers in real time.

```
                 SATELLITE (LEO)                     GROUND (Chennai, ISRO)
 .-----------------------------------.               .-------------------------.
 |  BB84 transmitter                |  QBER, key   |  BB84 receiver           |
 |   - random bases / qubit states  |  over the    |   - measurement + sift   |
 |  Eve attack injects errors ----->|---- link --->|   - error correction     |
 '-----------------------------------'              |   - privacy amplification|
                                                    '------------+-------------'
                                                                 v
         Phase 1: LinkPredictor (Gradient Boosting)  --> recommends QKD params
         Phase 2: EveDetector   (Hist-Gradient Boost) --> watches QBER stream
         Phase 3: GuardEngine (fusion) --> aborts key if INTRUSION confirmed
```

## Why this matters — in plain English

Satellites exchange secrets with ground stations (banks, governments, IoT
networks). Today's encryption keys are publicly *distributed* and can be copied;
a powerful adversary recording today's traffic can decrypt it later. **Quantum
Key Distribution (QKD)** fixes this: two parties derive a *shared secret key*
from the quantum-mechanical properties of single photons, and the no-cloning
theorem guarantees that *any* eavesdropping attempt perturbs the photons and
shows up as a higher error rate (QBER).

**The catch:** the atmosphere itself adds error. A naive operator can't tell a
*bad-weather pass* (high QBER, irrelevant) from an *intercept* (high QBER,
disaster). QU-AI-GUARD answers this with AI:

1. A **LinkPredictor** learns what QBER the measured link *should* produce, then
   **auto-tunes** QKD parameters to extract the most key in the pass window.
2. An **EveDetector** compares the *measured* QBER against the link-predicted
   value. The difference (the *residual*) is the signature of an eavesdropper:
   weather raises QBER predictably, Eve raises it *far above expectation*.
3. A **GuardEngine** fuses both models into one live decision, and is tuned to
   **minimise false alarms** — because aborting a real key costs a whole pass.

Everything runs locally. No cloud, no API keys.

## Reproduce the full pipeline

Run these four commands from the `quai_guard` directory. Everything is
deterministic given `--seed` (default 42).

```powershell
# 1) Simulate 200 satellite passes over the Chennai ground station
.\.venv\Scripts\python.exe -m src.pipeline.simulate_passes --n-passes 200

# 2) Run real BB84 QKD on every pass: clean, then three Eve attacks
.\.venv\Scripts\python.exe -m src.pipeline.run_qkd --eve none --strength 0.0
.\.venv\Scripts\python.exe -m src.pipeline.run_qkd --eve intercept_resend --strength 0.4
.\.venv\Scripts\python.exe -m src.pipeline.run_qkd --eve pns --strength 0.5
.\.venv\Scripts\python.exe -m src.pipeline.run_qkd --eve intermittent --strength 0.5

# 3) Train the AI guard (LinkPredictor + EveDetector)
.\.venv\Scripts\python.exe -m src.pipeline.train_ai

# 4) Evaluate honestly -> results/reports/evaluation_report.md + figures
.\.venv\Scripts\python.exe -m src.pipeline.evaluate
```

**Run the live demo:**

```powershell
.\.venv\Scripts\python.exe -m streamlit run app/app.py
```

Open http://localhost:8501 (or the URL printed). Pick a satellite and pass,

## What the evaluation report shows (honest numbers)

`results/reports/evaluation_report.md` is generated by the pipeline with
**hold-out** metrics — the models never see the test data:

| Metric | Value |
|---|---|
| AI auto-tune vs fixed config | **+65%** mean secure key rate (12 held-out passes) |
| EveDetector hold-out AUC | **0.873** |
| False-alarm rate at operating point | **2%** (tuned for low false alarms) |
| Precision / Recall | **0.99 / 0.45** (aggregate over all attacks) |
| intercept-resend detected | **65%** |
| intermittent detected | **68%** |
| PNS detected (stealthy design) | **12%** |
| Attack-strength sweep (IR) | 100% detected at strength ≥ 0.4 |

**Why recall is not near 100%:** the aggregate mixes *stealth-hard* attacks.
PNS (photon-number-splitting) is deliberately designed to barely perturb QBER —
in real systems it is countered with **decoy states**, not QBER statistics. The
report is honest about this instead of over-reporting. At a stronger operating
tolerance the FAR/recall trade-off is visible in the ROC figure
(`results/figures/eve_detector_roc.png`).

## How the quantum layer really works

- Each "round" builds a real `QuantumCircuit`: Alice prepares `n` qubits in
  random Z/X bases with basis bias `pZ`, Bob measures in random bases, and both
  **sift** to the matching subset.
- Noise is injected *as actual quantum-noise channels* on the circuit
  (`depolarizing_error` + `pauli_error`) scaled by the link model's elevation,
  atmospheric attenuation, background light and detector imperfections.
- Outcomes are measured on the **AerSimulator** with a seeded random
  measurement; error correction assumes an information-theoretic leakage
  `1 - 1.15 · h₂(QBER)`, and privacy amplification uses a seeded SHA-256
  compression. The result is a genuinely quantum-derived key, not a lookup.
- Eve attacks are applied during sifting (`intercept_resend` rebroadcasts Eve's
  basis/bit; `pns` only steals multi-photon pulses; `intermittent` targets a
  fraction of the pass), at a configurable strength.

## Assumptions & limitations (for the defence)

- **`pz`: basis leakage is not modelled**; the sifted fraction uses `1 - pZ` per
  basis with the known bias. A real system hides this with an agreed basis swap.
- **No quantum channel capacity limit** between samples: each sample yields a
  fresh rate; a real satellite pass interleaves uplink/downlink, so the absolute
  bps values are simulator-calibrated, not flight numbers.
- **Satellite pointing / beam divergence** is folded into `link_quality`
  heuristically, not a Gaussian beam model.
- **Decoy-state PNS countermeasure is out of scope**; instead the report is
  transparent that QBER-only detection cannot reliably catch low-strength PNS.
- All numbers are *simulated*. Validation on real QKD missions (EAGLE-1,
  QEYSSat) is future work.

## Faculty Q&A — ready answers

**Q: Is the QKD real or faked?**
A: Real circuits, executed on Qiskit-Aer with physical noise channels. The
"AI-guarded" part is the novel contribution: using the link context to separate
bad weather from an eavesdropper.

**Q: Why 96 photons per round?**
A: A compromise between statistical QBER variance and simulation time. The
parameters (`--n-photons`, config grid) are CLI-tunable; the maths
(EC-cost `1 - 1.15·h₂`, SHA-256) is independent of the block size.

**Q: How did you avoid overfitting the detector?**
A: strict fit/validation/test split (450/150/200), the threshold is calibrated
*only* on validation, and all reported metrics are computed on the untouched
test set. This is why the honest FAR is 2%, not the ~18% of a leaky evaluation.

**Q: What would you add next?**
A: (1) decoy states to close the PNS loophole, (2) a Gaussian satellite beam
model + real channel coupling, (3) a Kalman-tracked online detector that alarms
per-pass instead of per-window, (4) an uplink/downlink TDMA schedule for true
bps budgeting.
